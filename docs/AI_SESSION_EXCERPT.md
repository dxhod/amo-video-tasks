## 1. Вибір архітектури

### Асистент · 2026-09-06T13:56:35.126Z

Я б обрав **один репозиторій, вебзастосунок і окремий worker для FFmpeg, із чергою в Supabase**. Для цього тестового це хороший баланс: обробка відео ізольована від інтерфейсу, а інфраструктура залишається невеликою.

| Варіант | Переваги | Обмеження |
|---|---|---|
| Компактний моноліт | Найпростіший запуск і деплой | Рендер конкурує з API за ресурси |
| Web + окремий worker | Ізоляція рендера, відновлення завдань, спільні TypeScript-типи, без Redis | Потрібно коректно реалізувати чергу, повторні спроби та стани |
| Окремі frontend, API і worker | Незалежне масштабування компонентів | Більше сервісів, дві мови й більше інтеграційної роботи |

Supabase Queues надає постійну чергу на базі Postgres. Це дозволяє обійтися без окремого Redis, але worker однаково має безпечно витримувати повторне виконання завдання.

## 2. Модель монтажу та незалежних версій

### Асистент · 2026-09-06T13:56:35.126Z

Таймлайн має зберігати **інструкції монтажу**, наприклад: «взяти секунди 8–12 вихідного відео, потім секунди 0–4». Переставлення або розрізання сцени змінює ці інструкції; вихідне відео залишається цілим.

Під час запуску рендера зберігається **незмінний знімок таймлайна**. Результат прив’язується до конкретної версії та цього знімка. Тоді редагування під час обробки не призведе до ситуації, коли MP4 відповідає вже іншому монтажу.

Статус картки та статус обробки потрібно розділити. Картка може залишатися `in_progress`, поки рендер проходить `queued → running → succeeded/failed`. Старий рендер, що завершився пізніше, не має змінювати статус картки або замінювати актуальне відео.

### Асистент · 2026-09-06T14:43:28.900Z

### Асистент · 2026-09-06T14:56:49.246Z

Таймлайн зберігається як упорядкований список кліпів: стабільний ID, ID вихідного файлу, початковий і кінцевий кадри. Кінцева межа виключається; мінімальна довжина — один кадр.

Редагування зберігається з номером ревізії. За конфлікту двох вкладок сервер повертає `409`, а інтерфейс пропонує завантажити актуальний стан. Останній запис не повинен мовчки знищувати чужі зміни.

Створення рендера виконується однією транзакцією: перевірити права, ревізію й таймлайн; зафіксувати версію; створити job і повідомлення черги. Повторне натискання Render повертає наявне активне завдання.

## 4. Канонізація відео та точність FFmpeg

### Асистент · 2026-09-06T14:56:49.246Z

Після `ffprobe` worker готує канонічний MP4: H.264, 30 fps, AAC за наявності звуку, з урахуванням повороту та збереженням пропорцій. Довга сторона — щонайбільше 1920 пікселів без збільшення вихідного відео.

Зміни сцен визначаються через FFmpeg `scdet`. Канонічне відео використовується і для попереднього перегляду, і для монтажу, тому межі в кадрах відповідають одному медіаресурсу. Якщо змін сцен немає, весь ролик стає однією сценою.

Для рендера worker будує FFmpeg filtergraph із перевіреного знімка: обрізання відео й аудіо, скидання timestamps, конкатенація та кодування MP4. Для файлів без звуку використовується окрема гілка без звернення до відсутнього аудіопотоку.

## 11. Явний вибір версії для перевірки

### Користувач · 2026-09-08

Після рендера відео не повинно одразу переходити «На перевірку». Виконавець сам обирає готову версію, зокрема попередню, і натискає наявну кнопку «Передати на перевірку». На перевірці мають бути видимі лише оригінал і передана версія; після повернення — знову всі версії; у «Готово» — тільки прийнята.

### Асистент · 2026-09-08

Вибір версії в інтерфейсі раніше не змінював `current_version_id`, тому сервер перевіряв іншу версію. Рішення: передавати ID вибраної версії в наявній команді переходу, атомарно фіксувати її як `review_version_id` і застосовувати обмеження видимості через API, RLS та Storage. Завершення worker більше не змінює статус задачі.
