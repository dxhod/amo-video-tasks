# Технічні рішення

1. **Web + worker.** Два процеси ізолюють CPU-навантаження FFmpeg від HTTP. Один репозиторій і TypeScript дають спільний контракт таймлайна. SSR Auth налаштовано через `@supabase/ssr`.
2. **Postgres як координатор.** Команда користувача, фіксація версії та pgmq.send виконуються в одній транзакції. Немає проміжку «версія зафіксована, але завдання втрачено».
3. **Без редагування готової версії.** Перша команда Render фіксує timeline. Повторне натискання повертає існуючий job; зміни вносяться через копіювання версії. `revision` захищає від перезапису між вкладками.
4. **Кадри замість дробових секунд.** Робочий MP4 нормалізовано до 30 fps. Інтервали `[start,end)` спільні для UI й FFmpeg. Вихідний файл залишається незмінним.
5. **Fencing спроб.** `job_id + attempt + msg_id` і невичерпаний lease обов’язкові для heartbeat, помилки й результату. Протермінований worker не може привласнити завершення. Результати кожної спроби мають унікальні Storage-шляхи.
6. **Права у БД.** Browser не має INSERT/UPDATE на бізнес-таблиці. Авторизований RPC перевіряє членство, призначення та переходи; RLS обмежує читання і Storage. Service-role використовується тільки сервером.
7. **Прямий TUS upload.** HTTP API видає дозволений шлях, браузер передає файл у Storage. Помилка Telegram не блокує відео: outbox має окремий цикл.
8. **Вимірювання.** Середній рендер рахує тільки успішний FFmpeg render, без черги, скачування та upload. `done` рахується за виконавцем на момент завершення.

## Межі першої версії

- Один вихідний файл, одна відеодоріжка зі зв’язаним звуком, до 30 с / 50 MiB / 4K. Канонічне відео має довгу сторону до 1920 px, без збільшення.
- Монтаж без переходів, ефектів, довільних пауз, окремої музики, undo/redo та одночасного спільного редагування.
- HTML-video передперегляд може мати коротку паузу на переставлених фрагментах. Остаточний MP4 є точним результатом.
- Тривалі операції мають ліміт 10 хвилин; початковий concurrency — 1.
- Підписані посилання діють годину; сторінку потрібно оновити після закінчення доступу.
- При недоступності БД помилка пишеться у структурований stdout/stderr Railway; гарантувати її запис у недоступний Supabase неможливо.
- Відправка Telegram має семантику at-least-once: обрив після доставки може призвести до повторного повідомлення з тим самим error_id.
